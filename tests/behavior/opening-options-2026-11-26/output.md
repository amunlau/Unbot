## 任务A

Nova-LLM 平台的前缀缓存从提示起点按词元序列匹配，复用匹配部分的 KV 状态，并对未命中的后缀继续预填充。语义相近但词元不同的文本不构成可复用前缀。在共享提示、多轮历史和重复文档等场景中，前缀缓存可能减少重复计算，但这些场景本身并不保证命中。

词元前缀匹配后，混合使用全局注意力与滑动窗口注意力的模型还需确认对应 KV 状态有效；窗口状态已被淘汰时，即使文本重叠较长，也可能只能复用较短部分。全局注意力的 KV 状态随完整序列增长，滑动窗口注意力的 KV 状态主要保留有效窗口。Nova-LLM 已将两类状态分别放入两个缓存池，在预填充与解码阶段协调分配，并提前释放移出窗口的块。这样可避免为所有层都按完整上下文预留空间，节省的容量可供全局层或其他请求使用；池间分配还可结合预期序列长度调整。双池组织是已采用的方案，现有记录未证明它是唯一可行设计。

Nova-LLM 本版的层级前缀缓存为实验性功能，适用于共享前缀较长、工作集超出设备缓存且重算成本较高的情形。L1 位于设备，其保留的状态可直接参与计算；L2 位于主机，保留的状态在使用前需回传设备。前缀很短或复制已成瓶颈时，增加 L2 未必缩短响应时间。一次请求可以先直接复用设备中保留的部分，再回传仅存于主机的部分，最后重算未缓存的后缀。因此，命中长度不等于免搬运长度，相同命中率也可能对应不同的首词元时延。

## 任务B

1. 在低带宽链路上，当日志重复内容较多且压缩 CPU 开销较小时，归档服务压缩待上传日志可能缩短上传完成时间。CPU 已饱和或日志难以压缩时，启用压缩未必改善总耗时。

   适合侧重压缩的适用情形与资源限制。

2. 归档服务压缩日志后，上传字节数减少并不意味着端到端耗时一定缩短。日志需先压缩再上传，接收端随后解压，压缩环节也会占用 CPU 时间。

   适合侧重澄清数据量与总耗时的区别，并引出处理流程。

## 任务C

1. 【篇章与逻辑｜将适用情形强化为必要条件】“只有……才可能有益”排除了其他可能获益的情形；原资料仅报告已观察到的适合情形，未证明这三项条件均为必要条件。建议去除必要条件式限定，保留在所列情形下“可能”获益的判断。

2. 【依据待核｜频率判断缺少统计依据】“往往能更快完成”增加了收益出现频率的判断，原资料未提供相应统计；字节数减少本身也不足以推出总耗时缩短。建议回到资料支持的条件性可能，保留 CPU 已饱和或日志难压缩时未必改善总耗时的边界。

3. 未发现需标注的问题。该段首区分了字节数与总耗时，并指出压缩的 CPU 开销，判断强度与资料一致。
