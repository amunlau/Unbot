## 历史结果与当前复测

各目录说明中的日期、规则版本、程序测试数量和文字输出对应当时的执行。归档整理没有重新运行这些文字任务，也没有用当前规则指纹替换旧值。使用当前规则重测时另存输入版本、实际读取记录和新输出，再核对原有判据仍是否适用；已经读过或用于修订规则的材料应称为回归材料。

各次专项复测不能代替上述全部场景。程序测试核对工具、夹具和归档完整性，不给写作自然度、作者身份或未知稿件的准确率评分。需要检验写作判断时，必须实际执行选定任务并评阅输出。

## 归档完整性与指纹范围

[恢复清单](restoration-manifest.json)逐文件保存当次公开文件的 LF 摘要、整理前的原始字节与换行兼容摘要，并列出说明或元数据的整理位置。输入、实际输出和评阅判据保留原内容；说明及路径整理不改写执行正文或评阅结论。当前目录自身的总览、恢复检查摘要，以及 `current-validation-2026-11-25/`、`source-paragraphs-2026-11-26/`、`paragraph-constitution-2026-11-26/`、`opening-options-2026-11-26/`、`v4-release-2026-11-26/`、`density-review-2026-11-26/` 使用各自的更新和校验范围，不纳入这份历史文件清单。

旧清单中的 `archive_lf_sha256` 及原始字节摘要是历史收据，保留原值。遇到本次整理过的说明或元数据，测试将历史收据与恢复清单保存的整理前摘要核对，再以发布摘要检查当前文件；不会把旧摘要直接套在修改后的文件上。Git 将 CRLF 转为 LF 不应产生内容损坏误报。

规则索引中的文件摘要仍指向原执行版本，公开的 `files` 只列运行规则子集。已有 `sha256` 作为原集合摘要保留，新增的 `published_collection_sha256` 只核对当前列示子集。不能凭这个子集重新验证原全集，也不将历史文件摘要与持续修改的当前技能文件比较。

较早的记录没有独立加载收据，不补造加载证据。专业表达和读者任务的 `*-loaded.json` 只记录路径，核对去重和所属版本即可；带文件摘要的其他收据才逐项对照相应冻结版本。任务与结果文件的覆盖另行检查。

标准 `python -B -X utf8 -m unittest discover -s tests -v` 会执行[归档校验](../test_behavior_archives.py)。恢复后在 Windows、Python 3.14.7 的 LF 副本中运行全部 **139 项测试通过**（131 项工具与夹具、8 项归档，29.431 秒）；另在隔离副本中确认五种故意损坏均能被检出，验证后恢复副本原字节。程序与文档检查摘要见 [restoration-checks.json](restoration-checks.json)。以上为 v3.3.0 恢复归档时的记录，原始文稿工具和编辑规则未因该次恢复而回退；本版结果见上方 v4.0.0 专项检查。
